# M6 Ollama cloud: account connection and balance delivery plan

**Status: Draft; not approved.** This is one end-to-end implementation proposal, not evidence of an implemented capability or a passed milestone. The earlier approval of the local Ollama plan does not by itself approve this cloud credential design. The cloud proposal requires an explicit resolution of the credential-policy conflict below before code that handles credentials is implemented. No secret store, account, provider profile or cloud endpoint was accessed in preparing this document.

## Outcome and scope

An administrator can add any number of Ollama accounts through existing organization/account administration, connect each to an owner-provided official API key on the server, and see its actual cloud balance, freshness, history and applicable alerts. SDK and EAIS are examples of administrator-created groups, never hardcoded identities. The provider's documented balance variations and possible team sharing are preserved, not flattened into invented percentages. Local-model and process functionality remains in the approved local plan and the overall M6 plan; this plan covers the cloud work and its integration, not the whole milestone.

## Single recommended credential architecture — decision required

Use an **operator-provisioned Linux Secret Service item per connection**, accessed through the existing user session's Secret Service by a narrowly scoped, AgentMonitor-managed local credential boundary. The user creates the API key through Ollama's official UI, then enters it once into a no-echo local setup command on the machine running AgentMonitor. The command presents organization and account names from the registry for selection; no opaque IDs or key values are typed as command arguments. The dashboard displays an understandable setup instruction and connection state. It never accepts or retrieves keys over HTTP, including LAN HTTP. The application stores only a random non-secret binding reference, not a key, key fingerprint, prefix, length, or provider profile location. Rotation is the same local flow; deletion removes the managed binding and item, not the provider's original key. The user can independently revoke a key in Ollama.

A trusted local boundary retrieves the item only when needed, holds it transiently in memory to apply an authorization header to the one permitted request, and returns only validated non-secret observations and sanitized status. A managed Secret Service item **is persistent provider API-key storage**, and runtime retrieval **reads the key**. These facts must not be euphemized: the current root `AGENTS.md` says not to read or persist API keys, while project security/configuration policy also requires an approved managed-credential architecture. **This proposal conflicts with the literal invariant unless the owner explicitly directs an authorized policy change/exception applicable to the runtime. Approval of this draft alone does not automatically amend `AGENTS.md`.** Resolve the rule and record the architecture decision before any credential implementation; otherwise this slice is blocked. Coding agents never see the key even if a runtime exception is adopted. The existence of the system keyring does not establish provider endorsement, least-privilege key scope, or unlocked availability.

Reason for recommendation: per-account creation, rotation and removal do not require a service restart, and the already installed system service avoids introducing a new server. The dependency and threat review below remain mandatory. Same-user processes may access the keyring; Python/process memory cannot promise reliable zeroization. A locked or unavailable store, no interactive desktop, a missing session bus or a failed prompt produces a visible actionable unavailable state, never a plaintext fallback. Reboot/logout usability must be tested, not assumed. The initial setup is explicitly local; this is an intentional limitation for safe operation of the current HTTP LAN dashboard, not a silent promise of browser-based credential entry.

## Boundaries, contracts and data

Primary owner: Ollama provider adapter `M03`; supporting owners: `M02` registry, `M04` collection, `M05` capacity/history/alerts, API and `P02` dashboard. Implement through published versioned contracts; no adapter database access, domain-to-provider/framework/OS imports, dashboard-to-database access, or provider profile mutation. Update the OpenAPI contract and regenerate the client for any API extension. Inventory current contract versions during implementation: use compatible additive v1 changes only where valid; incompatible meaning or required fields require a versioned contract and migration/ADR, not an unannounced change.

* Registry: existing organization and account create/read/update/delete remain authoritative; provider selection is dynamic. Maintain a nullable opaque random `credential_binding_id` and non-secret state for each Ollama account, isolated to the managed credential component. Create records without credentials; edit labels/organization without changing the provider profile; disable/re-enable monitoring; rotate and disconnect locally. Account deletion removes its managed reference and, subject to explicit deletion semantics, its dedicated item; failures are reported for local cleanup. Never destroy a shared item while another record refers to it. No account email is inferred from a key.
* Connection state: `not_configured`, `pending`, `access_valid_identity_unresolved`, `unauthorized`, `rate_limited`, `store_locked`, `unavailable`; include sanitized observation time and actionable reason. Owner-entered name and organization are **owner asserted**. A successful balance GET proves access to that endpoint, not account identity, membership, team, or scope. Do not claim identity verification without authoritative evidence.
* Capacity: retain a versioned typed representation with `observed_at`, source and exact decimal USD amounts. Included-credit variant: `balance_usd`, `allowance_usd`, source period boundaries when supplied. Purchased credits: separate `balance_usd`, no invented allowance, percent or expiry. Legacy variant: separately labeled session/weekly `remaining_percent` and `resets_at` when supplied. Optional fields represent unknown, not zero; source-provided window/reset semantics and precision are retained. Reject malformed or unexpected responses safely rather than assuming their shape. Preserve original semantics through M05, history, API and built UI; use an additive discriminated schema if compatible, otherwise version it.
* Scope: a provider-proven shared pool can be represented once and related to multiple account records. Owner-described relationships carry `owner_asserted` provenance. If relationship is unknown, show each observation with its own unresolved scope and do not aggregate or present a combined total; do not deduplicate by email or claim multiple distinct pools. Alerts require comparable supported metrics and configured thresholds; no percentage alert for a monetary value without a real denominator. Stale values retain their observation time and stale label.
* Network: allow only HTTPS `GET https://ollama.com/api/balance`; reject redirects and arbitrary targets; set finite connect/read timeouts and response-byte limits, disable sensitive request/response logging, and report only allowlisted safe fields. No requests for models, prompts, source code, cookies, OAuth tokens or other provider content. Read-only upstream; no credentials in database, `.env`, browser, diagnostic output, evidence, backups, source or shell history. Avoid ever printing raw provider payloads or authorization headers.

## Rate and failure behavior

Ollama documents 10 balance requests per minute per user **across keys and devices**, with `Retry-After` on 429 ([official balance API](https://docs.ollama.com/api/balance)). As principal equivalence is unknown, serialize all cloud reads in one deployed AgentMonitor instance globally with at least 60 seconds between starts and bounded jitter; this is deliberately below the documented limit but cannot prevent other devices using the same allowance. Rotate fairly across enabled connections. Persist scheduler `next_allowed_at` and the parsed `Retry-After` deadline across process restart; when absent or invalid, apply bounded exponential backoff and jitter. No immediate retries, busy loops or cascading dashboard failures. Retain last successful observation as stale; surface 401/403, 429, timeout, network, unsupported response and locked keyring distinctly without logging secrets. A multi-instance deployment requires a shared limiter before it is supported. Natural recovery resumes fairly when allowed.

## Dependency, cost, operations and rollback

Candidate runtime dependencies are the existing system `secret-tool`/libsecret and Secret Service implementation (the workstation inventory found them installed, but not proven usable by the dashboard). Before adoption document exact versions, provenance, maintenance/security, transitive graph, licenses, notices and SBOM, and obtain the required admission; libsecret is LGPL-family and GNOME Keyring has GPL/LGPL components, but exact package obligations need review. No new Python or frontend dependency is assumed. Verify whether installed tooling supports the intended non-echo interaction and service session; do not assert it works based on package presence. Operational costs include local setup for each account, possible unlock after reboot, key rotation and monitoring of provider/API limits. API usage or billing implications and plan eligibility must be checked against the account's current official Ollama terms; no specific price or free allowance is assumed. The balance check itself must not initiate inference or purchase credits.

Roll out first to the existing local installation with the owner present for key provisioning, keeping the dashboard available; check existing providers before and after. Back up application data through the established procedure without exporting key material. Provide version-compatible rollback for schema/API changes and keep historic non-secret observations readable. Rollback removes/disables the managed integration only; no provider key revocation or default profile changes. Treat partially deleted references or locked-store cleanup as visible follow-up, not success.
