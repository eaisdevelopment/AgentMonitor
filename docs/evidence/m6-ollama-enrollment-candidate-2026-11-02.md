# M6 Ollama enrollment candidate — 2 November 2026

Scope: M6-T004/T005/T006, M6-A01/A03/A09 and FR-SAFE-001; composition with M02 `CTR-REG-011` 1.0.0 and approved Secret Service command. This is an intermediate candidate, not an M6 completion or live enrollment claim.

The candidate serializes credential transitions, owner enrollment, and Ollama account archive using a persistent account-scoped advisory flock under the approved database root. Enrollment needs a controlling terminal, creates a pending binding, runs the fixed `secret-tool store` command with inherited terminal descriptors, and activates only after success. A failed or interrupted operation leaves the pending item for later reconciliation and preserves any old active item. It contains no browser/API credential entry and does not touch provider profiles. Locks do not protect against uncooperative same-user software, and every future external store/clear path must use the same lock.

The pure lock-name test failed with module-not-found before implementation, then passed. The preexisting credential policy and command construction tests, real empty SQLite migration test, and real unattended-terminal rejection test passed: 17 tests total. Static lint passed. The unattended-terminal guard was separately run red before its module existed. Full red/green evidence for account-lock integration, coordinator and archive concurrency has **not** been established; they remain unverified and this candidate requires further review before production use. No fake provider, fake keyring, synthetic credential, live database, keyring item, or default profile was used.

Real owner enrollment, rotation, clear, crash recovery, simultaneous archive/store, cross-process contention, and the shared observation-commit generation fence are **Not Run**. Owner-friendly selection/entry point, recovery/cleanup operation and dashboard integration are not implemented. Migration remains v1_0709, with offline backup/upgrade and no downgrade; no new dependency is introduced. The approved system Secret Service dependency remains subject to its recorded limitations. No live service or database was changed.

Follow-up candidate adds `python -m agentmonitor.composition.ollama_credential_operator --data-root <absolute-directory>` for local account selection by organization and name. It uses the same enrollment flow for rotation; interrupted pending enrollment retries its existing account-scoped item. Owner-facing names are stripped of terminal control characters. The label test failed on missing operator module before implementation and passed afterward; focused tests and lint passed. Real interactive selection, successful secret entry, rotation, pending recovery and concurrent races remain Not Run. Cleanup deliberately remains pending: the installed `secret-tool` manual says clear removes matching unlocked items, which does not prove that a locked item has been removed. No Secret Service items were touched.

Lock-lifetime correction: the store child inherits the locked file descriptor; the parent closes its descriptor without explicitly unlocking the shared open-file description. A real disposable child test first failed with the descriptor helper absent, then passed: after parent death the lock remained unavailable until the child exited. A real `/usr/bin/secret-tool store` process attached to a disposable PTY also held the inherited lock after the parent closed its descriptor and released it on termination. No terminal input, key, or keyring item was supplied or stored. This proves behavior while the installed binary is waiting for input; it does not prove behavior after submitting a key or all D-Bus service-side crash cases. The child receives only a fixed PATH and explicitly selected session/display/locale variables; unrelated parent environment values are excluded. The environment allowlist test failed before implementation and passed afterward. Successful interactive enrollment, restart/logout, submitted-key crash cases and cleanup remain Not Run.

An additional candidate adds an internal M02-owned transaction-bound binding validator and an Ollama-specific M05 capacity commit method. The M05 write begins `BEGIN IMMEDIATE`, invokes the M02 validator on that same connection before looking up a receipt or writing, then commits the observation in that transaction. The validator checks the account-owned active binding and exact generation using `CTR-REG-011` 1.0.0; mismatched, rotated, disconnected, or archived binding states fail. The shared composition factory injects the M02-owned adapter port. The generic M05 writer can be configured to require a credential fence; the Ollama composition does so and rejects an unfenced call. Existing Claude/Codex commit routing remains unchanged. A future Ollama collection admission/sink must exclusively use that configured writer: the general writer remains callable without a fence, and this candidate does not claim to close that admission path. No public HTTP contract or schema changes were introduced. This adds an internal transactional adapter interface; its integration with the future Ollama collection writer is still required.
