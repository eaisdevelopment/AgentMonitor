## 1. Ownership, schema, and authorization identity

`v1_0100` has parent `v1_0000` and creates exactly seven M01-owned tables: `iam_administrator`, `iam_browser_session`, `iam_api_token`, `iam_api_token_scope`, `iam_login_throttle`, `iam_idempotency_record`, and `iam_security_audit_event` ([DB revision matrix](../plans/persistence/sqlite/plan-v1.md) §8; M2 Task 1). M01 owns their semantic DDL and repository ports; the single migration steward attaches the revision to the Alembic head and edits `backend/migrations/catalog.toml`. No cross-module FK, eighth IAM table, alternate head, HTTP bootstrap row, seeded administrator, or implicit startup DDL is permitted. The migration starts uninitialized. Atomic IAM security-audit rows are local M01 facts; **M2 publishes no cross-module IAM outbox**. The M01 plan, contract-adoption and baseline now defer `CTR-EVT-001` consumption by M01; any later M01 event producer requires separate synchronization and migration, never an unreviewed eighth table.

M2 authorizes a codified **fresh, absent-file initialization** through the real Alembic chain to `v1_0100`. An existing `v1_0000` database is classified `upgrade_required` and protected-service startup fails closed; it is never silently altered, replaced, or deleted. Existing-database upgrade remains outside M2 until the approved backup/quiescence/recovery workflow exists. The migration catalog pins both immutable revision bytes and one head; tests prove the old M1 file is preserved and an empty new file acquires exactly the seven IAM tables. No backup prerequisite is waived for an existing database.

M01 is the sole verifier/policy authority for `CTR-IAM-001..008`; P01 maps policy to `CTR-API-001..003` and `CTR-COMMON-005`; P02 consumes only generated `CTR-UI-001`. M01 domain/application imports neither FastAPI nor ORM nor UI. P01 imports published M01 ports, not IAM repositories. P02 reads neither backend nor database. M01 owns its module/adapter paths and semantic contract; the integration steward assigns the shared `identity_access_v1.py` writer, migration/catalog writer, composition writer, and sole OpenAPI/generated-client artifact writer before parallel work ([ownership manifest](../plans/parallel-ownership.toml)).

## 2. Password, session, CSRF, and throttle policy

| Concern | Proposed exact V1 decision | Owner / source |
|---|---|---|
| Administrator/bootstrap | One implicit administrator, password-only, no username, default password, HTTP setup/recovery, password argument, or persistent plaintext dashboard password in `.env`. Owner enters/confirm password at a protected controlling TTY; only a salted Argon2id PHC verifier and non-secret policy version persist. Bootstrap is an exclusive singleton transaction with one safe audit row. | M01 + local operator adapter; M01 §§2–3, 8; `FR-IAM-001/002`. |
| Password input | Bootstrap/change: minimum 15 Unicode code points, maximum 1,024 UTF-8 bytes, no composition rule or implicit normalization; allow paste. A bounded plausible login candidate reaches one real verifier when initialized and not throttled, even if below the creation minimum. No password echo, body logging, password-derived unkeyed fingerprint, or credential-specific error. | M01 §3; P01 bounds; security review. |
| Hashing | Argon2id with independent random salt and PHC parameters; rehash after successful verification only. The [Linux admission](../dependencies/m2-argon2-admission.md) fixes the RFC 9106 low-memory profile: 65,536 KiB, three passes, four lanes, 16-byte salt, 32-byte tag, PHC version 19; at most two simultaneous hashes. Target Linux benchmark passed p95 250 ms / peak RSS 256 MiB budget. No weaker configuration, custom hasher, or fake verifier. | M01/security/dependency reviewer. |
| Browser session | OS-CSPRNG credential with at least 256 bits; random selector plus digest stored, never raw cookie. New login makes new session+CSRF binding. Idle expiry 1,800 s, absolute expiry 43,200 s, activity write coalesced at 60 s; `as_of >= expires_at` is expired, idle never extends beyond absolute, terminal state never resurrects. Server-side revocation survives restart. | `CTR-IAM-003/005`; M01 §3 and IAM config baseline. |
| CSRF | Separate at-least-256-bit random secret, digest bound to exactly one active session. Unsafe cookie-authenticated request requires CSRF cookie value, equal `X-CSRF-Token` header, and matching stored digest. Missing/malformed/cross-session/expired proof returns one safe denial. Login has no pre-session CSRF but exact Origin; pure bearer has no ambient-cookie CSRF. `SameSite` is defense in depth, not the sole control ([OWASP CSRF guidance](https://cheatsheetseries.owasp.org/cheatsheets/Cross-Site_Request_Forgery_Prevention_Cheat_Sheet.html)). | `CTR-IAM-003`, `CTR-API-002`; M01 §3, P01 §13.3. |
| Throttle | One durable installation-global bucket. Five failed initialized logins in a 900-s window trigger a 30-s lock; each consecutive lock doubles duration, capped at 900 s. Throttled attempts skip Argon2 and return bounded `Retry-After`. Window expiry or successful login clears failure count; success clears consecutive-lock count. No IP, user agent, password property, or raw request body is retained. Concurrent increments/locks are transactional. | M01 §3 and IAM config baseline; exact transition tests before acceptance. |

The selected timeout/throttle/retention values are fixed M2 policy, not performance evidence. Their permitted configuration ranges are singleton values in the M01/configuration baseline; environment, CLI, API, and test settings may not alter them. Future configurability requires versioned security review. Pure policy tests use explicit UTC `as_of`; T2/T3/T4 use real time, SQLite, server, and browser, never a patched clock.

## 3. Local HTTP/cookie perimeter

Canonical V1 local authority is one configured `http://127.0.0.1:<port>` origin; bind only `127.0.0.1`, derive the sole trusted `Host` with that port, and reject aliases/duplicate or malformed Host. The installed default port is `43110` (override allowed from 1 to 65535 after availability check); real tests may use an ephemeral loopback port `0` owned by the test runner, never as installed configuration. No `localhost`/IPv6 alias, forwarding-header trust, wildcard CORS, non-loopback bind, or remote mode is inferred. Login and any cookie-authenticated unsafe request require **exact** canonical Origin; a cookie GET/HEAD with Origin must match if one is sent. Pure bearer requests are Origin-independent and scope-limited, with no ambient cookie or CORS grant; this resolves P01 §13.3's unqualified GET/HEAD Origin statement in favor of the M2 Task 6 bearer test. Host remains strict for every request. Reject cookie-plus-bearer before M01 as `400 ambiguous_credentials`, not M01's competing `multiple_authentication_credentials` ([P01 §13.1](../plans/api/fastapi-boundary/plan-v1.md); M01 §4).

Freeze cookie names `agentmonitor_session` and `agentmonitor_csrf`. Both are host-only (`Domain` absent), `Path=/`, `SameSite=Strict`, and capped by session absolute expiry; session is `HttpOnly`, CSRF is readable only so the generated client can echo it. On verified local plain HTTP, `Secure=false`; TLS/remote needs a separate approved profile and `Secure=true`, not a V1 flag. Do not use `__Host-` on local HTTP because its Secure requirement conflicts with this profile ([MDN cookie guidance](https://developer.mozilla.org/en-US/docs/Web/HTTP/Guides/Cookies)). Setting/clearing uses matching attributes; auth/token responses are `Cache-Control: no-store, private`. Credentials never enter URL, browser storage, OpenAPI examples, logs, screenshots, or evidence. Swagger is authenticated after setup, bearer authorization is non-persistent, and its reviewed local request transport **must omit cookies** whenever bearer authorization is entered; working bearer “Try it out” is required by `FR-IAM-006` and cannot be disabled as a fallback ([P01 §13.4](../plans/api/fastapi-boundary/plan-v1.md)).

Residual local threat: browser cookies are scoped to host, not TCP port, so another local HTTP service at `127.0.0.1` could receive them if the owner visits it. Host/Origin checks defend AgentMonitor from hostile requests but do not make cookies port-private. Malicious local processes **remain untrusted** under the [security architecture](../architecture/security.md); owner-only files, no bearer token in browser storage, short-lived/revocable sessions, strict Origin/Host, CSRF, and no wildcard CORS reduce but cannot eliminate same-user process risk on plain loopback HTTP. Root security review accepts this disclosed residual within the existing local-only profile, without relaxing the threat model or representing it as a passing adversarial test. A stronger local-process isolation design needs a separately approved origin/TLS or browser credential architecture.

## 4. Bearer token wire/lifecycle and M2 route authorization

Approved M2 token wire format: `am1.<selector>.<secret>`, where selector is 16 random bytes and secret is 32 random bytes, each unpadded base64url; reject other versions/alphabets/lengths without echoing them. Store selector and SHA-256 digest of the **full high-entropy token**; verify with a safe comparison. A digest of this randomly generated 256-bit secret is not a human-password hash. The bounded display prefix derives only from the public selector, never from secret bytes. Active-token cap is 64; name length is 1–80 Unicode code points and at most 256 UTF-8 bytes, duplicates permitted because token ID is identity. Expiry is mandatory: default 90 days, allowed 1 hour–365 days from issue, evaluated at `as_of >= expires_at`; no unlimited V1 bearer token. These values are the root/security decision within the owner's approved M2 scope, not a test invented after implementation.

Only M2-realized bearer scopes are issuable in this milestone: `read:diagnostics` and `write:tokens`. Other proposed V1 scope names stay reserved but unavailable until their owning API operations are approved; an old token must not silently gain authority when M3+ routes appear. `write:tokens` bearer principals may create/rotate/revoke only a subset of their own scopes and manage only tokens within that attenuation rule; a successor's expiry cannot exceed its bearer issuer's expiry. The browser administrator may manage all tokens. No bearer can call browser-only session/password routes. P01 maps every M2 operation to one permission before invoking M01; the following is the proposed `CTR-API-001` operation matrix ([P01 §12.1](../plans/api/fastapi-boundary/plan-v1.md)):

| Method/path | Operation ID | Auth / permission | Success and mutation condition |
|---|---|---|---|
| GET `/api/v1/iam/initialization` | `iam_get_initialization_v1` | pre-auth loopback / none | 200 coarse setup state; no credential detail |
| POST `/api/v1/session` | `iam_login_v1` | pre-auth exact Origin / none | 204; fresh session+CSRF cookies; no idempotency key |
| GET `/api/v1/session` | `iam_get_current_session_v1` | cookie only / `read:self` | 200 safe session summary + version ETag |
| DELETE `/api/v1/session` | `iam_logout_v1` | cookie only / `write:self` | 204; valid session+CSRF+current ETag, terminal revoke |
| PATCH `/api/v1/session/password` | `iam_change_password_v1` | cookie only / `write:self` | 204/fresh cookies; CSRF+current-session `If-Match`+idempotency; M01 also compares administrator version within the transaction |
| GET `/api/v1/iam/sessions` | `iam_list_sessions_v1` | cookie only / `write:sessions` | 200 bounded page, no bearer |
| DELETE `/api/v1/iam/sessions/{session_id}` | `iam_revoke_session_v1` | cookie only / `write:sessions` | 204; CSRF+target-session `If-Match` from its list-item strong ETag, terminal revoke |
| POST `/api/v1/iam/session-revocations` | `iam_revoke_other_sessions_v1` | cookie only / `write:sessions` | 200 safe summary; CSRF+idempotency |
| GET `/api/v1/api-tokens` | `iam_list_api_tokens_v1` | cookie or bearer / `write:tokens` | 200 bounded page |
| POST `/api/v1/api-tokens` | `iam_create_api_token_v1` | cookie or bearer / `write:tokens` | 201 one-time plaintext; CSRF if cookie, idempotency |
| POST `/api/v1/api-tokens/{token_id}/rotations` | `iam_rotate_api_token_v1` | cookie or bearer / `write:tokens` | 201 one-time successor; CSRF if cookie, `If-Match`+idempotency |
| DELETE `/api/v1/api-tokens/{token_id}` | `iam_revoke_api_token_v1` | cookie or bearer / `write:tokens` | 204; CSRF if cookie, `If-Match`, terminal revoke |
| GET `/api/v1/iam/security-events` | `iam_list_security_events_v1` | cookie or bearer / `read:diagnostics` | 200 bounded safe audit page |

Create/rotate succeeds once, atomically with scopes, predecessor state, idempotency receipt, and safe audit row. A repeat that first passes current authentication and authorization returns `409 one_time_secret_not_replayable` and safe resource ID/version/state only, never plaintext. A key reused for different safe canonical metadata returns `409 idempotency_key_reused`; a password-change key never stores a raw or unkeyed password-derived request fingerprint—an authenticated replay is a safe non-replay conflict. The required `Idempotency-Key` header is exactly 16–128 bytes matching `[A-Za-z0-9_-]+`, with no whitespace, quotes, or commas; storage is digest-only and receipt retention is 86,400 s. Password-change receipts are scoped to stable administrator principal+operation so a fresh login can see the safe conflict. Token-management receipts are scoped to the authenticated issuer credential/principal context and operation, with current scope attenuation and target authority rechecked before any safe metadata is returned; separate bearer credentials under one administrator never share a receipt. For password change, the old cookie is revoked by success: retrying with it returns `401 dashboard_authentication_required` before receipt lookup. After a fresh successful login, a currently valid session with exact Origin, CSRF, and `write:self` may present the same key and receive `409 one_time_secret_not_replayable`; the completed receipt is checked before stale `If-Match` or old-password evaluation. No receipt is available to an unauthenticated caller. Rotation cannot create two successors under concurrency. Explicit revoke/rotate nulls the old digest while preserving safe historical metadata; expiration is enforced on read. Physical cleanup of expired verification digests belongs to the M01 bounded retention port, invoked by a later M08 scheduler or an explicit protected maintenance command; no M2 automatic purge is claimed. A bearer trying to revoke itself may receive 401 on a later replay because the credential is then invalid; this is not a successful replay.

Password change verifies current password, updates PHC and administrator version, revokes **all existing browser sessions**, then issues one fresh current session/CSRF pair atomically. Existing API tokens remain active because they are independent credentials; the owner may revoke them through existing token-management operations, and M2 adds no unplanned revoke-all flag. M2 includes an explicit local forgotten-password recovery command: it requires quiesced service/exclusive TTY and revokes **all** sessions and API tokens before readiness; no HTTP reset or fallback credential. Test that command on an isolated real SQLite installation and document the owner procedure; the real owner's recovery is Not Run unless actually requested. Post-restore invalidation is a later M01/M08 integration policy, **Not Run in M2**; a restored database must fail normal readiness until that integration is approved and executed, not inherit active restored credentials silently.

## 5. Safe HTTP outcome and retention/bounds freeze

Every app/framework non-success response is `SafeProblemV1` with stable `code`, safe title/status/correlation ID, no submitted credential/body/PHC/digest/SQL/path. Uvicorn/h11 may reject malformed framing or duplicate `Host` before ASGI; those pre-app denials cannot carry an app-generated problem/correlation header and are the sole parser-level exception. Proposed M2 mappings reconcile [M01 §4](../plans/modules/m01-identity-access/plan-v1.md) and [P01 §11](../plans/api/fastapi-boundary/plan-v1.md):

| HTTP | Public code | Exact M2 meaning |
|---:|---|---|
| 400 | `ambiguous_credentials` | cookie and bearer presented together; P01 transport denial |
| 401 | `invalid_dashboard_credentials` | bounded wrong login; M01 internal `invalid_credentials` maps here |
| 401 | `dashboard_authentication_required` | protected route has missing/malformed/unknown/expired/revoked session or bearer; never provider reauth |
| 403 | `origin_not_allowed` / `csrf_validation_failed` / `permission_denied` / `scope_escalation_denied` | distinct safe perimeter/proof/permission denials, with no credential-existence disclosure |
| 404 | `api_token_not_found` | only after management authorization; no anonymous existence oracle |
| 409 | `one_time_secret_not_replayable` / `idempotency_key_reused` / `credential_state_conflict` | distinct one-time replay, key reuse, or terminal-state conflict; not an active target's stale version |
| 412 / 428 | `precondition_failed` / `precondition_required` | `If-Match` stale on an otherwise authorized active conditional mutation, or absent on a required conditional mutation |
| 413 / 415 / 422 | `request_too_large` / `unsupported_media_type` / `password_policy_violation` | bounded transport/schema/policy errors, never submitted value |
| 429 | `login_throttled` | durable IAM throttle; bounded `Retry-After` and no attempt count |
| 503 | `iam_setup_required` / `iam_repository_unavailable` | uninitialized local installation or unavailable IAM store; no hash/schema/path details |

For a **valid** logout request, require CSRF and return 204 after revocation/clear-cookie. For a missing, expired, or revoked session, choose 401 `dashboard_authentication_required` plus clear presented cookies, not M01's Draft proposal of anonymous 204; this preserves P01's browser-cookie-only route profile. The UI treats 401 as logged out. If reviewers instead require anonymous 204 cleanup, that changes the auth-profile registry and must be approved/tested before route implementation. `provider_reauthentication_required` is a separate future provider outcome, not an M2 login/expiry code.

Retention: safe IAM security events and terminal session/token metadata are kept 365 days; active credentials/admin persist while active. Completed idempotency receipts expire after 24 h; cleared throttle buckets after 30 days; purges are bounded/audited and never delete active credentials. M01 audit rows exclude token names, raw IP/user-agent, payloads, keys and values. Token/session verification digests are null on explicit terminal transitions and are not exported; an expired credential fails immediately even before physical cleanup. Database backups remain owner-only and sensitive because they may contain live PHC/digests. M2 tests use only production bootstrap/use cases on isolated real file-backed SQLite, no direct seeded rows.

Transport bounds: JSON auth/token request body at most 8 KiB; password field at most 1,024 UTF-8 bytes; token name as above; credential-bearing header/cookie value at most 512 ASCII bytes; idempotency key 16–128 ASCII bytes; list limit default 50, maximum 200 with opaque cursor; no raw free-form audit metadata. At most 64 request headers and 16 KiB aggregate header bytes are accepted before credential extraction. The local server admits at most 32 concurrent requests, with a 10-second total request deadline except bounded streaming of the prebuilt static shell; password hashing has the stricter two-concurrent budget. The P01 implementation must enforce/test these rather than relying on framework defaults.
