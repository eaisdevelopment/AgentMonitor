# M6 migration lock continuity seam

The existing service-quiescence and owner-association-settings lock contexts now yield sealed, root-pinned live leases. The current `AUTO-MIGRATE` operation can consume both held leases and a preassigned private backup ID, allowing a future controller to hold the same locks across the migration rather than release and reacquire them. Existing CLI behavior remains available. Leases are invalidated on context exit, validate the pinned directory and lock inode/owner/mode, and reassert a nonblocking exclusive flock. These are internal trusted-process capabilities; they do not defend against deliberately importing private issuer internals or independently malicious same-user code.

On baseline `df9a289`, the real SQLite preassigned-backup/held-lock test failed because `run_upgrade` did not accept existing leases. With this change it passed: a competing migration was refused, the migration used the preassigned backup ID, both held leases validated during migration, wrong-root and root-permission changes were rejected, and both leases failed validation after their contexts exited. Three existing real empty-database upgrade checks for `v1_0603`, `v1_0707` and `v1_0708` passed too. Ruff passed. A fake/wrong-issuer lease was not exercised as an I/O fixture; issuer and exact-type restrictions were independently reviewed.

This is an internal seam, not a deployment, restore, dashboard restart or M6 acceptance result. Full controller integration, crash recovery, staged restore and live installed-data verification remain Not Run. No live database or service was modified.
